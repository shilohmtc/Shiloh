# Client Insights

Accepted direction: a separate, read-only Workspace Client Insights page keeps the Directory alphabetic and compact. Directory cards show non-clickable Next appointment and Last recorded visit boxes; names still open the client profile. Individual Overview details remain available.

Insights defaults to two calendar months including the current month to date, with a five-month option. Exact dates and the partial current month are labelled in Africa/Johannesburg time. Monthly recorded-client-visit counts and distinct clients cover the entire authorised period, not just the visible Directory page. Rankings show 20 clients per page, highest visit count first; equal counts share rank and display alphabetically. Each row opens its existing profile and preserves the Insights period/page and original Directory search on return. Last visit in the ranking is within the selected period. Each ranking row also shows the most-received treatment within that same selected period, rather than reusing the 12-month Overview. A treatment counts once per linked visit per client, using service identity and the latest recorded nonblank snapshot name. Equal leading counts are shown as ties (up to three names, with any additional tie count). Incomplete service identities or treatment details suppress a definitive leader; inaccessible private treatments are never included. This describes recorded use, not personal preference.

Only ended completed and no-charge appointments linked to the canonical profile count. Linked treatment appointments count once per client. Guests remain separate; names, phone numbers and organiser details never merge identities. Cancelled, no-show, pending, future and legacy-only unlinked records are excluded. These are recorded visits, not lifetime coverage, forecasts or retention rates. A typical interval follows the existing conservative four-distinct-date rule; sparse or irregular history makes no usual-pattern claim.

The query reuses existing lookup and clinic/private appointment scope. It uses a read-only transaction, 3-second acquisition limit, 2-second statement limit and 250ms lock limit. A 10,000-appointment safety cap, ambiguous cross-day linked visits or failed reads produce an unavailable state rather than partial totals or invented zeros. No cache, new permission, database migration, client/financial writes or messages are introduced. Tests use fictional data, including PostgreSQL cohort coverage, guest/group boundaries, permission denial, empty/error states, accessible phone/desktop journeys and preserved navigation. Exact release evidence belongs in the pull request.
