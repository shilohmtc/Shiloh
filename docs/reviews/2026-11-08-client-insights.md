# Client Insights

Accepted direction: a separate, read-only Workspace Client Insights page keeps the Directory alphabetic and compact. Directory cards show non-clickable Next appointment and Last recorded visit boxes; names still open the client profile. Individual Overview details remain available.

Insights defaults to two calendar months including the current month to date, with a five-month option. Exact dates and the partial current month are labelled in Africa/Johannesburg time. The summary cards use “Total visits” and “Individual clients”; the subtitle and history caveat keep clear that these are recorded-history counts. Monthly recorded-client-visit counts and distinct clients cover the entire authorised period, not just the visible Directory page. Client cards show 20 clients per page, highest visit count first; equal counts display alphabetically, without numeric ranks. Accepted refinement, 9 November 2026: compact non-clickable rounded bubbles show visits, last recorded visit and usual interval, with treatment underneath in a matching full-width informational bubble and explicit insufficient-history wording. The accepted 9 November copy tidy-up uses “Most frequent clients”, removes repeated visible SAST abbreviations, and presents the comparison cutoff once in plain English while retaining Africa/Johannesburg calculations. Short notes preserve the completed/no-charge, access, incomplete-history and non-preference boundaries; detailed counting rules remain documented here and enforced in the existing service. Each row opens its existing profile and preserves the Insights period/page and original Directory search on return. Last visit in the ranking is within the selected period. Each ranking row also shows the most-received treatment within that same selected period, rather than reusing the 12-month Overview. A treatment counts once per linked visit per client, using service identity and the latest recorded nonblank snapshot name. Equal leading counts are shown as ties (up to three names, with any additional tie count). Incomplete service identities or treatment details suppress a definitive leader; inaccessible private treatments are never included. This describes recorded use, not personal preference.

Only ended completed and no-charge appointments linked to the canonical profile count. Linked treatment appointments count once per client. Guests remain separate; names, phone numbers and organiser details never merge identities. Cancelled, no-show, pending, future and legacy-only unlinked records are excluded. These are recorded visits, not lifetime coverage, forecasts or retention rates. A typical interval follows the existing conservative four-distinct-date rule; sparse or irregular history makes no usual-pattern claim.

The individual-client comparison always covers the current and previous two calendar months, independently of the selected two- or five-month summary. It counts each canonical profile once per month, across the full authorised cohort, from the first day to the same SAST day and time (rounded down to a minute) in every month. Only appointments ended by that matching cutoff qualify. If any month lacks today's day, all three cutoffs include the whole latest common day, with that limitation and exact ranges visible. Those completed-day cutoffs stay fixed rather than moving backwards the next morning. This avoids comparing a partial current month or day with a longer prior period. The existing monthly visits chart still shows full past months and explicitly incomplete current-month activity. Older and unlinked histories remain limitations, not zero-confidence claims or inferred identity matches. No projections or percentage-change claims are added.

The queries reuse existing lookup and clinic/private appointment scope. Each uses a read-only transaction, 3-second acquisition limit, 2-second statement limit and 250ms lock limit. A 10,000-appointment safety cap, ambiguous cross-day linked visits or failed reads produce an unavailable state rather than partial totals or invented zeros. The comparison uses a separate bounded read with the same scope and cap; if it fails, its unavailable state does not erase independently verified selected-period totals. No cache, new permission, database migration, client/financial writes or messages are introduced. Tests use fictional data, including PostgreSQL cohort coverage, guest/group boundaries, permission denial, empty/error states, accessible phone/desktop journeys and preserved navigation.
