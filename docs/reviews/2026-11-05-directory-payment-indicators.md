# Client Directory payment review

## Scope and authority

This increment adds asynchronous review indicators under each client name. The Directory and live search render independently; a slow financial read cannot block name search. The authenticated GET uses current client lookup, appointment view, payment view, all-business Calendar and all-service authority. The existing clinic relationship must exist for every requested ID. Tenant, private-service, legacy/dual-link and unauthorized group-member coverage is restricted rather than treated as settled. Each group's members are checked before a shared position is exposed. The endpoint is private/no-store; actor identity is server-bound.

One repeatable-read READ ONLY snapshot enumerates all directly linked modern CRM appointment records for the page, with no latest-visit or reporting-month filter. Each completed/no-charge subject is evaluated once through the same canonical account and settlement functions used by booking payment summaries. Applied rewards, gift vouchers, welcome vouchers, treatment credit, prior payments/transfers, refunds and recorded receipts retain existing definitions. Unused wallets do not count as payment. The summary mode omits receipt notes, payment-link details and noncash history metadata; the calculation itself is unchanged. Full payment screens retain those details.

The card never sums group balances into individual client debt. It distinguishes recorded completed-visit balances, shared-booking review, price/exceptional-payment review and upcoming deposit review. Upcoming deposits use the existing read-only Dashboard deposit projection, only when the selected clients have future scheduled/confirmed appointments. Provider-paid money without ledger evidence and the existing exceptional-receipt audit categories are review flags, including on cancelled records. Missing or invalid canonical prices require review without hiding other clients’ verified positions. A no-balance label applies only to linked completed visits; it is not a claim that every historical identity or future obligation is settled.

## Completeness and bounded work

A page accepts at most 24 distinct positive client IDs. Reads admit at most 1,000 linked appointment rows, 1,000 group-member rows and 500 distinct completed payment subjects. Each statement has a two-second timeout, and elapsed work is checked against five seconds between subjects and before commit. Any exceeded limit, malformed position or read failure discards the whole projection and returns unavailable. Restricted client coverage discards that client's subtotals. There is no partial-to-zero fallback. An abandoned browser request stops further subject reads and rolls back the snapshot. The browser stops waiting after ten seconds and suppresses late responses after search replacement. The client Appointments tab remains the existing detailed review destination.

A local PGlite synthetic workload with 120 completed bookings and 2,400 ledger entries returned all 120 outstanding indicators in 1,522 ms with ledger count unchanged. This is a local workload observation, not production latency or proof of actual historical completeness. An initial fixture without practitioner assignments was correctly restricted; the measured run used valid synthetic staff/service assignment. A larger 500-booking/10,000-ledger-entry workload reached the five-second guard at 5,009 ms and returned unavailable, with the ledger unchanged; it did not return partial counts. Limits, cancelled requests and failure semantics are independently tested.

## Verification and boundaries

Synthetic tests cover older unpaid visits, shared account deduplication, future deposits, partial receipts and applied rewards, restricted/private/legacy scope, missing group authority, price and exceptional-payment review, unknown clients, permission revocation, duplicate membership, malformed values, query/workload failures, zero writes/notifications, and session-bound private HTTP reads. Phone/desktop/narrow Storybook states, accessibility, existing live search and delayed-response isolation are reviewed. No real client/payment records or communications are used for verification. No database migration, financial rule, paid service, credential or permission change is included.

Return-rate analytics remain blocked on verified historical coverage and stable identity; no refused database route has been retried. Persistent business targets still need a separately reviewed storage/authority decision. Those features are not implied by these indicators.
