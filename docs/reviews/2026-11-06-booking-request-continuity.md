# Individual request booking continuity

An individual flexible request previously opened a generic Calendar week without its client. Arrange booking now opens the existing booking form with a server-read active canonical client, the requested date where valid, and a fixed return to the originating Dashboard request. Staff still choose treatment, eligible practitioner and time, review the exact client and mobile, and explicitly confirm. No booking or client write occurs when opening the form. Group/couples requests retain their existing paths and identities.

Existing clients and Add new client remain the two choices. Name/mobile search is immediately visible, begins after 300 ms with at least two characters, and retains the explicit Find client/Enter alternatives. Results require explicit selection. Editing the query clears the old selection and review; generation checks discard late responses after another query, selection or mode change. A carried client remains selected when the choice enhancement initializes.

## Boundaries

The server reuses current booking-create and client-lookup authority, returning only the existing masked client projection. Invalid IDs, inactive/missing clients and revoked authority fail closed. The existing prepare/confirm authority rechecks client identity, mobile, scope, revisions and availability. The return destination only accepts the fixed Dashboard request anchor, never an arbitrary URL. A pending review must be discarded successfully before navigation; failure retains the form and its error. Ordinary Calendar prefill/history and Week/All staff return behavior remain intact.

No database schema, permissions, phone identity policy, financial logic, client messaging policy or production records change. Optional phones for new group guests require a separate identity/organiser-contact decision and are not implemented here. Broader unfinished payments and post-completion rewards remain separate increments.

## Validation

Synthetic service and HTTP checks cover authorization, active clients, strict identifiers, masked output, no opening writes, editable dates and safe returns. Browser checks cover phone/desktop layout and accessibility, automatic search and stale responses, explicit selection, exact carried-client prepare payload, and failed/successful discard navigation. The existing authenticated synthetic booking browser proof retains new/existing-client identity, explicit review and confirmation safeguards.

The Rebook evidence guard accepts only the exact fixture's individual client/date/return link and anchor change. Negative tests still reject altered client IDs, dates, return targets, appointment/practitioner IDs, labels and scripts. Sixteen before/after screenshots retain the five individual/shared/group/couples action variants with zero submissions.

Local review is not production acceptance. Exact-head CI, merge, deployment SHA and live verification are recorded on the PR and existing roadmap. No live client, booking, payment or message is used for testing.
